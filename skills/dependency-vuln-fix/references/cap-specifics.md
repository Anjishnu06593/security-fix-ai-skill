# SAP CAP specifics (Node.js and Java)

Things that make CAP projects different from a plain npm/Maven repo. Verify each against the
actual project: layouts vary.

## Project shape

```
db/  srv/  app/        CDS models, services, UIs
package.json           root manifest (CAP Node *and* usually CAP Java: cds-dk, build scripts)
mta.yaml               multi-target app descriptor (BTP Cloud Foundry)
pom.xml                CAP Java: root pom (+ srv/pom.xml, sometimes db/ or app/)
gen/  or  srv/src/gen  generated by `cds build`: never edit, never fix findings here
```

- Findings may name **any** of several lockfiles/poms: root `package-lock.json`, `app/<ui>/package-lock.json`,
  `db/package-lock.json`, approuter `app/router`... Fix the file in the finding's `File` field, then
  grep the other lockfiles for the same package.
- **CAP Java still has a Node side**: root `package.json` with `@sap/cds-dk` runs CDS build via
  `cds-maven-plugin`. Node findings can appear in a Java repo and vice versa.
- `gen/` output contains a generated `package.json`/lock for deployment. Fix the *source* manifest
  and rebuild; do not patch `gen/`.

## Key packages and how they upgrade

| Package | Notes |
|---|---|
| `@sap/cds` | CAP Node runtime. Major versions have breaking changes: read the CAP release notes/migration guide first, never bump a major as a side effect of a CVE fix. Patch/minor within the major is normally safe. |
| `@sap/cds-dk` | CLI, usually devDependency; keep major aligned with `@sap/cds`. |
| `@cap-js/*` (db drivers, telemetry, audit-log...) | Peer to a specific `@sap/cds` range: check `peerDependencies` before bumping. |
| `@sap/xssec`, `@sap/xsenv`, `@sap/hdi-deploy`, `@sap/approuter` | Security-relevant SAP libs: prefer the version SAP recommends in its security notes; approuter/hdi-deploy have their own `package.json`. |
| `@sap/hana-client` / `hdb` | Native module: install scripts/prebuilds; keep `--ignore-scripts` for analysis, test the real build. |
| `com.sap.cds:cds-services-bom` | CAP Java BOM (property usually `cds.services.version`). Bumping it moves many `cds-*` artifacts together: run the full test suite. |
| `cds-starter-spring-boot`, `cds-adapter-*` | Pull in Spring Boot; the Spring Boot version is typically a separate property/BOM import in the root pom. |
| Spring Boot parent/BOM | Use Boot patch releases for Tomcat/Jackson/Logback/SnakeYAML issues where possible; otherwise Boot's version properties. |

Many transitive findings in CAP apps come **through** `@sap/cds`, `@sap/xssec`, `@sap/approuter`,
`@sap/hdi-deploy` or `cds-dk`. First check whether a newer *patch/minor* of that parent already
fixes it (`npm view <parent> dependencies` / `versions`); a parent bump is better than an override.

## MTA / pipeline interactions

- `mta build` normally runs `npm ci` (builder `npm-ci`) per module, or `npm install`/`npm` builder in
  older setups: check `mta.yaml` `build-parameters`. With `npm ci` a **lockfile out of sync = build fails**.
- Each MTA module that has its own `package.json` has its own resolution: an override in the root
  `package.json` does **not** apply to `srv/package.json` unless that module installs from the root.
- Node runtime: `mta.yaml`/`manifest` buildpack version and `engines.node`; do not accept a fix that
  needs a newer Node than the buildpack provides.
- Java: `jdk.version`/`maven.compiler.release` vs target runtime (SapMachine buildpack version).
- `cds build --production` must still succeed (`verify.py npm --cds-build`).

## What to run to be confident

Node: `npm ci` -> `npm ls <pkg> --all` -> `npm audit --omit=dev` -> `npx cds build --production` ->
`npm test` -> (optional) `cds watch` smoke test.
Java: `mvn dependency:tree -Dincludes=<g:a>` -> `mvn verify` -> (optional) `mvn spring-boot:run` smoke test.

## Behaviours to never change as a side effect of a CVE fix

Auth configuration (`xs-security.json`, `requires.auth`), service bindings, CDS models/annotations,
Java/Node runtime versions, build parameters in `mta.yaml`.
